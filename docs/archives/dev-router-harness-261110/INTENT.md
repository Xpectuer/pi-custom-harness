基于 custom Pi 制作 router agent，减少用户管理多个 session 的负担。
本轮目标是简洁接口与 mock，不是真实 worker 后端。

## 默认审查

| 用户行为 | 本轮变化 | 需要决定 | 如何验收 |
| --- | --- | --- | --- |
| 向 router 交代任务，查询进度，获取结果；由 router 查询跨 session 上下文 | 用户批准 v6 的需求内容，记录为 v7 授权基线；无新增需求 | Q-1、Q-2 已确认；无阻塞需求决策，具体 API 留待规格阶段定义 | 用户只问一次整体进展；router 汇总各项状态与已完成结果，无需用户逐项提供 ID、切 session 或复制结果 |

## 问题与使用场景

用户需要在多个 Pi session 之间管理任务并搬运上下文。
期望由 router 统一指挥 workers，连接 session 间的上下文。
router 不应拥有普通 Pi agent 的直接读写文件与 Bash 权限。

## 预期结果

- 用户交代工作后，只需问一次整体进展；router 查询各项工作、收取已完成结果并汇总（R-1、R-3）。
- router 能查询上下文，支持跨 session 协作（R-4）。
- router 的工具权限收敛到协调接口；worker 保留完整 Pi 能力（R-2、R-7）。
- 接入方实现约定接口即可替换 mock，无需改动 router 业务逻辑（R-5、R-6）。

## 范围与关键待决

- 范围内：基于 custom Pi 的 router、worker 管理接口、上下文查询接口与 mock。
- 范围外：真实 worker 执行、真实上下文后端、真实沙盒实现。
- 后续版本：workflow 定义与管理。一个 workflow 可由多个 workers 分工或并行完成。
- 硬约束：router 不直接读写文件或运行 Bash；worker 拥有完整 Pi 默认工具与沙盒 workspace。
- 本轮只模拟 worker 契约，不将 mock 描述成真实执行或隔离。
- Q-2 已确认采用 Pi extension；Q-1 已确认按需统一汇总，本轮不要求主动通知（D-4）。
- 整份需求已获批准并记录为 v7；范围为 R-1 至 R-7 与 S-1 至 S-10，R-8 仍属范围外。

## 讨论记录

### D-1 决策：五项最小能力命名（2026-11-10）

- 状态：已批准（来源：用户会话，结构化回答 d1=approve）
- 背景：用五个清晰动词覆盖用户已提出的两组功能。
- 影响：关联 R-3、R-4、R-5；批准能力命名基线，不定稿具体 API。
- 决定：采用 dispatch、list、inspect、collect、queryContext，规格阶段据此定义输入、输出、状态与错误语义。
- 理由：用户未说明；所选方案将进度查询与结果收取分开表达。
- 被拒方案：将 collect 合入 inspect；暂不固定命名。用户未说明拒绝理由。
- 后果：保留五项独立能力；本次不构成整份 INTENT 的批准。

| 候选操作 | 用途 | 应向 router 提供的信息 |
| --- | --- | --- |
| `dispatch` | 派活给 worker | 用于继续跟踪该工作的标识 |
| `list` | 查看有哪几桩工作 | 工作清单及各自状态摘要 |
| `inspect` | 查看一桩工作的完成情况 | 该项工作的当前进展 |
| `collect` | 收取工作结果 | 该项工作的结果或尚未完成的事实 |
| `queryContext` | 查询跨 session 上下文 | 与查询有关的上下文及来源 |

“收活”不自动等同于合并代码、删除 workspace 或销毁 session。
这些动作未被用户要求，不应暗含在 `collect` 中。
命名建议不预设一次工作对应一个长期 worker，亦不预设查询后端。

### D-3 决策：采用 Pi extension 入口（2026-11-10）

- 状态：集成入口已批准；其余技术建议未单独批准。
- 来源：页面回复 Q-2 明确选择“A：Pi extension”。
- 决定：采用 Pi extension，复用 Pi CLI；同步 R-1、S-1 与集成约束。
- 理由：用户未说明额外理由；所选方案复用 Pi CLI，减少自建入口代码。
- 被拒方案：B（SDK 自建入口）、C（独立后端服务）；用户未说明拒绝理由。
- 授权边界：仅批准集成入口，不自动批准持久化策略、具体 API、主动通知或整份需求。
- 关联：Q-2；R-1、R-2、R-5、R-6。
- 已核实：现有示例使用 TypeScript、Pi ExtensionAPI 与 TypeBox（`examples/custom-tools.ts:1-2`）。
- 现有调研记录：extension 可收紧工具集；SDK 可创建自定义 session（`docs/pi-custom-tools-research.md:30-39,97-107`）。
- 已知约束：优先 extension / SDK，不修改只读归档（`AGENTS.md`）。

| 候选 | 技术组合 | 优点 | 成本与限制 |
| --- | --- | --- | --- |
| A：Pi extension（已选） | TypeScript + Pi CLI 的 Node 运行时 + TypeBox；进程内 mock | 复用现有 Pi 终端入口、会话与模型接入；延续本仓库示例 | 扩展运行在 Pi 生命周期内；未来主动报告需核对事件能力 |
| B：Pi SDK 自建入口（未选） | TypeScript + Node.js + Pi SDK + TypeBox；进程内 mock | 自行组织 session 生命周期与对外入口 | 需要维护启动、事件输出与退出处理；不能假定自动获得完整 Pi CLI 交互 |
| C：独立后端服务（未选） | Pi extension 薄适配 + HTTP 服务 + mock | 接口可由不同语言实现，进程可独立部署 | 增加协议、服务启动与连接失败处理；当前没有独立部署需求 |

技术建议（非本次入口选择的额外授权；规格阶段细化）：

- 工具参数沿用 TypeBox；后端契约用 TypeScript interface。
- mock 先存内存，不引入数据库、Web UI 或编排框架。
- 内存 mock 重启后丢失状态；是否需要跨重启持久化尚未获批准。
- 不选择真实 worker 的沙盒、部署与存储技术，本轮不实现这些后端。
- Node 最低版本按现有 Pi 调研为 22.19.0；实际开发依赖版本在规格阶段锁定。
- 模型供应商与应用技术栈分开；既有 DeepSeek 401 是调用验证阻塞，不因此更换模型。
